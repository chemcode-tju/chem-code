# Chem-Agent 7×24 与 Super-Agent 生产模拟测试矩阵

2026-11-19 · 验收设计

用同一套验收验证从 Slurm、外部消息和定时检查收到事实，到正确的任务线程判读、受控提交、科学验收和用户通知的全过程。最高优先级是**作业不被重复提交、已接收事件不丢、回执待核对的动作不重放、旧事件不推进新尝试、科学失败不放行下游**。遇到故障时，用户应能看到发生在哪一层、系统已做什么、下一步能否自动恢复。

本矩阵覆盖现有 Codex／agy 首版、独立 Slurm 监控，以及拟接入的持久入口、调度和通知能力。跨后端运行中交接是后续能力，首版按现有代码验证方案确认后锁定分配。每行是一个待执行用例，具有相同前置条件的变体可参数化。现有测试只是基线，覆盖范围见文末。 [7×24 架构](always-on-computation-agent.md) · [Super-Agent 设计](super-agent-product-design.md)

## 测试环境与通过条件

| 层级 | 环境与运行方式 | 独立证据 |
| --- | --- | --- |
| **T0 单元与契约** | 冻结 UTC 时间、注入可控单调时钟，使用固定数组、错误日志和状态序列。测试数据及期望 JSON 入库版本化。 | 归一化事件、匹配、去重键、时间计算、解析结果和权限判据。 |
| **T1 服务集成** | 临时 SQLite、普通项目目录、模拟模型和 SSH/Slurm。调用真实 API、派发器、工具及回执。用测试屏障逐点暂停并在独立子进程注入 `SIGKILL`。浏览器验收通过真实页面及测试服务器执行。 | 独立 fake Slurm 命令计数、数据库前后快照、工作目录哈希、模拟后端 RPC 记录、界面可见状态。 |
| **T2 双集群预生产** | 两个隔离 Slurm 实例，各建非生产账户和独立工作目录。脚本只造产物和退出码，接入实际队列服务、SSH、文件系统和进程管理器。Codex／agy 可先接协议替身。 | 直接从两个调度器查 `squeue`／`sacct`，对照平台事件与回执。测 NFS 迟读、守护进程重启、记账差异及跨集群限速。 |
| **T3 真实端验证** | 用获准的测试实例、账号和项目目录验证真实 Codex／agy 及远端集群。先进行只读观测与接管演练，再用获准的低资源短作业验证提交与回收。 | 脱敏原生线程 ID、后端版本和有效模型参数、Slurm 作业 ID、提交脚本哈希与科学产物清单。 |

**P0** 是相关能力开放前的阻断项。**P1** 是质量、容量或运维验收项。表里的测试层级是最低要求。启用自动提交前，应在 T2 用真实 Slurm 再跑一遍影响提交、取消、数组、身份和 accounting 的 P0 用例。真实端后端能力、集群权限和时间间隔由该验收环境配置记录。

每例记录集群、项目、方案版本、任务、尝试、事件、待办、run、原生线程、动作、Slurm ID 及各自时间戳。断言至少覆盖**用户看到的状态、持久账本、外部实际副作用**三层。特别要检查失败分支的外部命令次数为零，以及重启前后 fake Slurm 的提交次数相同。用 `event_id` 等标识检查因果关联，具体文案和模型措辞可变。每个测试至少记录一次下一轮轮询或重启后的状态，避免把暂时未发生的重复当作通过。

### 故障注入与重试判据

| 已确认的事实 | 自动处理 | 用户或操作员的恢复操作 |
| --- | --- | --- |
| 读取或模型准备失败，确认尚未发出写动作 | 有上限地退避，保留原待办和检查点。`429` 遵守 `Retry-After`。 | 恢复账号或权限后重试原事项。 |
| 模型或工具请求已发出，结果未知 | 保持待核对。检查后端回执、工作目录和 Slurm 记录，其他无依赖事项继续。 | 在可验证证据下补确认或重新授权。记录原因、操作者和对账依据。 |
| 已确认动作成功，后续入账、发信或页面刷新失败 | 复用已提交回执，补写投影或补发通知。 | 打开原待办和作业，核对原动作，无须重新提交。 |
| 计算失败或未通过科学判据 | 保留尝试和产物，阻塞依赖。可按授权及预算执行已定义的恢复动作。每次重算单独记录。 | 查看判据、前后参数和成本，选择重算、接受替代结果或结束。 |

崩溃测试用屏障固定位置，涵盖**外部调用前、请求已发出但未拿到响应、收据已落盘但方案未更新、run 已完成但通知未发**。分别观察正常关闭和强杀进程。单次调用失败使用精确错误码，长时故障切断相应来源或后端并持续至少两个轮询/租约周期。测试工具在隔离环境保存实际调用计数，模型回复里的「已提交」不能当提交证据。

## Slurm 观测、归属与计算动作

| ID / 层级 | 前置与注入 | 预期处理与通过证据 |
| --- | --- | --- |
| SL-01 P0 T1 | 集群 A、B 有相同数字 job ID。A 再模拟同 ID 回绕复用，两个账户订阅同一分区。 | 根据集群、作业实例或运行身份及授权路由。两次独立运行各关联自己的产物。错误账户、旧作业和错误目录均无投递或取消。 |
| SL-02 P0 T2 | `squeue` 消失，`sacct` 先为空，若干周期后才出现终态。变体为 `squeue` 超时、`sacct` 权限不足或暂停。 | 等待记账或显示观测不可用，期间 0 次科学成功/失败唤醒；有效终态到达后对应实例只产生一条待办。队列恢复后补扫。 |
| SL-03 P0 T2 | 存在已结束的作业，停止监控跨多个轮询周期。恢复后重叠回扫；再分别模拟历史保留到期和跨过旧窗口的迟到记录。 | 恢复可查终态且去重。对源端不能证明的区间标记缺口，游标不能把未读页跨过去；人工补查保留来源和审计。 |
| SL-04 P0 T2 | 数组仅部分结束，父记录先显示整体状态。混合成功、超时、失败和取消，替换一个元素后再查。 | 逐元素核对，用预期集合和已批准的汇合策略决定整组。缺项或非允许的失败阻塞下游。异常汇总可定位元素与运行实例。 |
| SL-05 P0 T2 | 抢占或显式 requeue，注入旧运行终态交错到达；再测缺少实例字段的旧集群。 | 当前运行继续被观测，旧终态留痕并标过期。在无法区分时进入待核对。0 次以旧尝试的文件发起新步骤。 |
| SL-06 P0 T2 | 注入 `TIMEOUT`、`OUT_OF_MEMORY`、`NODE_FAIL`、`PREEMPTED`、`CANCELLED`、非零退出码，以及不同命令的状态格式。 | 保留原始调度证据和各自原因。重排或恢复建议受当前尝试和授权约束。取消不触发自动重提。未识别的状态保留未知和原字段。 |
| SL-07 P0 T1 | 对同一任务用同一提交 key 并发两请求。第二轮重试分别使用完全相同及修改过的脚本/参数。 | 同请求复用同一子节点、动作和 Slurm ID。变更的载荷冲突并可定位原请求。调度器只收到一次 `sbatch`。 |
| SL-08 P0 T2 | `sbatch` 成功接单后故意丢失响应。子情形为后来只找到一个匹配、搜不到、找到多条或短时 accounting 不可用。 | 唯一匹配自动归档原 job ID。其余保持 `uncertain` 有证据可查，0 次盲重提，其他作业照常推进。 |
| SL-09 P0 T2 | 配额先拒绝，随后释放。重复释放事件；再注入无效分区、账号不允许、提交脚本语法失败。 | 配额项可等配额并消费一次释放，成功接受的作业只有一个。永久配置错误清楚报告并阻塞该项；0 次无限循环或静默换分区。 |
| SL-10 P0 T2 | 取消与完工重叠，或 `scancel` 后丢失响应。再尝试对已被另一个运行复用的 job ID 取消。 | 保留取消请求及最终权威终态，不能凭请求直接写已取消。以原作业身份核对回执，违规取消 0 次，用户可识别谁发起了操作。 |
| SL-11 P0 T2 | 接管外部正在跑、已经结束或无权读目录的作业；两次并行接管同一作业。 | 只绑定证据匹配的现有作业；接管期间 `sbatch` 为 0。相同执行权不重复授予。目录或身份存疑时保持未接管。 |
| SL-12 P0 T2 | 迁移 observer 时在旧端禁用前、新端启用后分别断网；让两个位置都读到同一终态。 | 当前代次有且只有一个有效观测所有者。重复读取入箱去重。旧观察不能覆盖新状态，observer 只读，`sbatch`／`scancel` 为 0。 |
| SL-13 P1 T2 | 大量作业同时完成，A 集群每次超时，B 正常。覆盖畸形记账行、历史查询字段缺失及完成日志轮转。 | A 退避并暴露错误、最老未补观测和查询频率。B 按正常周期更新。坏行隔离，轮转和重查不漏已可获得的终态。 |

## 持久收件箱、会话争用与恢复

| ID / 层级 | 前置与注入 | 预期处理与通过证据 |
| --- | --- | --- |
| EV-01 P0 T1 | 同一来源事件在一次及多次请求中重复，分别来自重叠订阅和彼此独立的订阅。 | 相同来源 ID 对应一条事实。相同语义动作只建一件待办，独立订阅目标仍各收到一次。带不同正文的同 ID 进入冲突状态。 |
| EV-02 P0 T1 | 桥接从上游分页读取，在落库之前、之后尚未 ACK、ACK 之后分别强杀。再以部分成功的批次恢复。 | 源端确认覆盖已落库范围，未入库的还可补送。已接收项重投后仍只有一条。按源游标与最终 ID 集合证明无缺口。 |
| EV-03 P0 T1 | 已匹配等待但生成待办的事务失败。变体为待办入库后、路由之前进程重启。 | 事务回滚后等待还可重新匹配。持久化后待办可继续路由，同一个等待实例只有一次命中。 |
| EV-04 P0 T1 | 注入迟到的旧尝试终态、乱序状态和重复文件事件。生成待办后修改方案、重跑节点或撤销规则。 | 领取和写动作前校验当前版本与尝试。过期事件保留审计和跳过原因，0 次旧文件发布或过期提交。 |
| EV-05 P0 T1 | `all` 等待 A、B 都可用，`any` 等待任一异常，另有会到期的文件等待。并发在到期边界投递和取消。 | 依据事务顺序和明确的时间边界仅做一个终止决定。`any` 证据只包含命中分支，`all` 等齐。到期/取消后重启仍无迟到唤醒。 |
| EV-06 P0 T1 | 用户同一会话正在发消息，两个 worker 同时认领该会话的后台事件。重复 API 请求、刷新页面，再停止正在运行的回合。 | 同一执行会话同时最多一个 run。优先处理已排队用户请求。待办与请求 ID 可查询，后台事件等候。停止的回合禁止后续未经核对的写动作。 |
| EV-07 P0 T1 | 批次含 12 项，Agent 处理 3 项、登记 1 项等待，随后崩溃或仅回复「全部完成」。 | 已确认的 3 项保留且不重复。等待项有持久条件。剩余 8 项仍可领取。对照逐项回执和实际工具记录，整批不能随文本回复被确认。 |
| EV-08 P0 T1 | 分类、纯模型请求、持久工具意图、外部调用和检查点提交分别中途重启。 | 已保存工具结果从检查点读取，确认未发出的可重试，已发送结果未知的进入对账。重启前后实际写动作计数符合预期。 |
| EV-09 P0 T1 | 租约工作者停止续期然后“复活”，新工作者已领取。再模拟旧工作者发出的 Slurm 动作晚返回。 | 旧代次不能写平台状态。外部结果可作为证据对账到原动作，不能用旧 worker 推进下一步。目标资源独立阻塞。 |
| EV-10 P0 T1 | 已保存完成 run，尚未更新方案 JSON/进度投影或站内通知时强杀。 | 重建所缺投影与发送记录，原 run 和作业沿用。最终结果、通知及方案各自收敛，0 次额外模型轮和提交。 |
| EV-11 P1 T1 | 入箱存在版本未知或无法解析的有效载荷；同一队列后面有正常事件。重放失败项时选择只重建历史。 | 坏事件入可查询隔离列表，保存原因和游标。正常事件继续。历史回放不会自动执行科研操作。 |

## Super-Agent 后端、分配与权限

| ID / 层级 | 前置与注入 | 预期处理与通过证据 |
| --- | --- | --- |
| AG-01 P0 T1 | 主对话分配 Codex 与 agy 两张卡，分别指定模型、强度。另测同一个实例上的两张卡。 | 从 RPC 参数验证有效设置，每卡只有自己的原生线程以及工作目录写入范围。主对话历史只出现认可的摘要和结果引用。 |
| AG-02 P0 T1 | 两人同时编辑草稿或两个标签页用相同方案版本保存。单独改变预设版本、停用实例、确认后再尝试修改。 | 旧版本获得清晰冲突，可刷新并核对。确认后的版本快照稳固。当前首版应返回分配锁定。缺失/失效配置有明确恢复操作，无静默模型切换。 |
| AG-03 P0 T1 | 产生 `step_ready`，再令不同父研究步骤下的子作业同时结束，包含任务专属等待。 | 依 `parent_task` 或显式等待找到正确任务。方案读取按归属会话，领取与续跑按执行会话。断言每条待办只出现在对应原生线程，旧方案仍走已有主会话路径。 |
| AG-04 P0 T1 | 会话新建发送成功但原生 ID 尚未持久化时强杀。再在绑定落库后、首次工具调用前重启。 | 有唯一回执时对账登记原线程，无证据时显示待核对。已绑定的从原 ID 恢复。0 次由未确认绑定的线程调用提交工具。 |
| AG-05 P0 T1 | 后端返回 session busy、暂时网络错误、`429` 和 `503`，分别出现在恢复会话前及回合发送之后。 | 确认未发出时，按上限和错误类型重试原请求。发出后按实际回执对账。核对没有多次创建线程、重复 run 成功记录或提交。 |
| AG-06 P0 T1 | 模型流中断、超时或工具响应返回前断开。另测试上下文压缩失败后重新拉起。 | 保存安全检查点并保留原线程。未知工具动作先对账。超出预算停在可见状态，其他线程继续运转。 |
| AG-07 P0 T3 | 真实实例登录失效、指定模型或强度消失、线程文件丢失；模拟 SSH 上下文目录无法打开。 | 报告发生在哪一层及影响任务。恢复同实例/原会话后继续。无原线程时需显式交接，保留前记录和 Slurm 作业。 |
| AG-08 P0 T1 | agy MCP bridge 无法建立、请求超时、回调后丢失 ACK。Codex 丢工具回执、重放同 call ID。 | 工具仍按平台的动作 key 和作用域鉴权。未执行的调用有可重试状态，可能执行的调用先对账。关闭连接后的任务临时 socket 和子进程可回收。 |
| AG-09 P0 T1 | 同一任务审批重复弹出、双点击批准、拒绝、超时，以及通过主对话或其他任务尝试答复。 | 只有所属用户/任务可决策。同一次授权只消费一次。拒绝、到期或串错线程的审批没有副作用，重启后仍查到最终决策和执行情况。 |
| AG-10 P0 T1 | 同方案 A 卡等待审批或已进入 busy，B 卡已就绪，主对话有新消息。再让 A 的回执进入待核对。 | B 和主对话在设定并发额度内继续，A 的事项保持可见。检查派发选择次数、B 启动时间和进程锁，避免按方案级排队把整组卡住。 |
| AG-11 P0 T1 | 在计划暂停、权限撤销或用户叫停后，让延迟的 Agent 工具调用报告成功、提交、取消或改数据。 | 平台按实时状态及工具作用域拒绝过期动作。远端已确认在跑的作业仍可只读跟踪；停止 Agent 回合和取消计算有独立记录。 |
| AG-12 P0 T1 | 使用错误用户、工作区、方案、步骤、作业或产物引用调用受控工具。测试越界路径、链接重定向和无权分区。 | API 与工具层均拒绝且不暴露其他项目的正文、路径或结果。外部命令 0 次，提供可追踪且脱敏的拒绝记录。 |
| AG-13 P0 T1 | 同方案两个任务几乎同时报告，各自使用同一旧方案版本。再重复其中一条报告。 | 并行报告采用版本检查，安全重试后两个独立节点结果都保留。相同报告可去重，不能丢一个结果或覆盖第三个节点。 |
| AG-14 P0 T1 | 后续启用运行中交接时，在旧线程有已领批次和外部作业的情况下转交。新旧实例同时返回。 | 新分配只处理未发出的待办。保留原回执与在途作业，显式确认归属。旧分配的迟到写入被拒绝，新线程引用同一作业。首版对应 AG-02 锁定用例。 |

### 实施顺序与验收记录

1. **先补首版保护测试。** 以 SL-07/08/10、EV-02/07/08/10、AG-03/08/10/11/13、SC-01/02 为核心。先固定同方案忙会话、逐项完成与远端不确定三种高风险复现，再按入口→记录→派发→工具建立自动化。这组用例覆盖重复提交、错路由、阻塞其他任务和错误放行下游。
2. **接入双集群和真实后端。** 用 T2 跑过数组/requeue、迟到记账、观察迁移以及进程崩溃边界。T3 分别记录 Codex 和 agy 的部署版本、模型和真实 SSH 差异。新后端加入时复跑 AG、EV 和 SC 的核心契约。
3. **为新入口设独立验收。** 外部事件启用前通过 TR-01 至 TR-04；定时功能启用前通过 TR-05 至 TR-09。通知渠道启用前通过 UX-02/03。运行中转交启用前通过 AG-14。未接入能力在验收结果标为待实现。
4. **发布前做容量和操作演练。** 关闭客户端与后台服务，注入网络和磁盘故障，恢复快照，执行峰值及长跑。核心不变量要求 **0 重复外部提交、0 越权动作、0 已确认入口事件无解释丢失、0 科学失败被默认放行**。报告吞吐、峰值资源和实测恢复时间，记录硬件及配置。容量指标按达标、偏离或未测试逐一记录。

每次执行以 `case_id + 版本 + 层级 + 环境 + 变体/种子` 标识结果。证据包括前后状态、外部命令计数、重放输入、脱敏链路和涉及的用户页面。状态用「通过」「失败」「环境阻塞」「待实现」「未运行」，并在失败项记录最小复现、缺少的恢复行为及下一次验收条件。

| **T1 先复现同方案顺序阻塞（AG-10）** | 同一已确认方案含两个无依赖步骤，先启动 A 并将其等待审批固定在屏障上。登记 B 的 `step_ready` 并提交一条主对话用户消息。在 A 的屏障保持关闭时，断言 B 已进入自己的原生线程，主对话完成回复，A 只有原 run 和原审批。测试条件是至少有两个任务槽位和独立的交互额度。重复一轮，让 A 的下一项待办走 `session_busy` 或 `uncertain` 分支。失败报告包含 `offer` 选择顺序与三个目标的 run 记录。 |
| **T1 验证终态入箱的提交与 ACK 顺序（EV-02）** | 固定三个上游事件，桥接每页两条。分别在平台入箱提交前和提交后、源 ACK 前终止进程。每轮重启后完整排空两次。断言源 ACK 对应的平台事件均已存在，三条事实各一条，第三条按顺序进入收件箱。断开模型也应能验证收件箱。 |
| **T1+T2 验证接单后回执丢失（SL-08）** | 把动作固定为一个授权请求。fake Slurm 或预生产调度器已产生 job ID 时断开返回通道，再重启平台并重复投递原请求。首次让记账不可用，确认平台的查询次数有界且 `sbatch` 累计为 1。恢复记账后只匹配一个 job ID，核对已登记 ID 等于实际接单 ID。零条和多条匹配各留一组，确认仍待核对，并核对无关作业的读和判读已继续。 |
